# product-recommendation

## 何时使用

- `b2c-need-discovery` 给出了需求、场景和约束，销售准备说"适合你的是哪一款"时。
- 客户直接问"你们哪个适合我""这两个有什么区别""我要买哪个"。
- 客户在多个套餐之间摇摆，需要一个基于事实的选择依据时。
- 客户的需求其实**不适合**某产品，需要诚实说明并给出替代方向时。

前置条件：需求不清楚或置信度不足时，**先不要推荐**，转入提问流程。

## 要做什么

1. **确认前置条件**。检查需求判断：`scenario` 是否明确？`constraints` 是否覆盖关键硬条件？`confidence` 是否够用（参考：低于 0.6 视为不足）？不满足就先提问，从 `unknowns` 里取最多 2 个最关键的问题。
2. **取证**。用 `get_product_policy` 拿到候选产品的权威事实：适用场景、功能与限制、价格与政策、生效期。用 `search_phrase_cards` 拿对应的已审核话术卡，作为表达方式的参考（不是事实依据）。
3. **逐条比对**。把客户已确认的需求与产品事实对齐，写出：哪一条需求被满足、靠哪条事实支撑、哪一条需求**不被满足**。
4. **给出一个主推荐**，最多再给一个备选。说明推荐理由和**不适用条件**——什么情况下这个推荐是错的。
5. **给出下一步**，且必须是低压力动作：继续确认信息、看资料、预约演示、申请试用、留下联系方式以便跟进。不含任何自动发送、自动外呼、改价或折扣动作。
6. **标注依据**。每个事实引用带上来源、版本、生效期；政策里没有的数字一律不写。

## 提问优先规则

出现以下任一情况，本轮输出以提问为主，不输出推荐：

- 使用场景不明；
- 关键硬约束未知（团队规模、必须配套的系统、使用频率等）；
- 客户在比较两个方案，但说不出自己在意的点；
- 需求置信度不足，或转写质量差导致理解不确定。

提的问要能直接问出口，一次最多 2 个，并说明为什么问（帮客户判断，不是审问）。

## 输出结构

推荐不是固定 JSON，但必须包含以下六项，缺一不可：

```text
推荐：<产品/套餐名>
推荐理由：
  - <已确认需求> → <对应的已审核产品事实>（来源 · 版本 · 生效期）
不适用条件：
  - <什么情况下这个推荐不合适>
备选（可选）：<产品/套餐名 + 一句话区别>
下一步：<低压力动作一句话>
依据：<政策条目 id / 版本；话术卡 id>
```

如果任何一项拿不到事实支撑，写"当前无可用依据"，不要猜。

## 硬性约束

- **必须引用已审核产品事实**。推荐理由中每条都要对应 `get_product_policy` 返回的内容；没有依据就不能写进理由。
- **必须写不适用条件**。只讲优点的推荐是不合格的输出。
- **不为转化率强推更贵套餐**。客户需求用基础方案就能满足时，就推荐基础方案；价格更高的方案只有在解决已确认需求上有实质差别时才提，并说明差别具体在哪。
- **不制造升级焦虑**。不用"以后一定会不够用"作为推荐理由，除非政策里明确写了容量或次数上限，且客户已确认会超过。
- **不比较未审核的竞品信息**。客户提到竞品时，只讲自家已核实的事实，不贬损对方。
- **数字只来自政策**。价格、优惠、有效期、退款条件、配送时效，必须逐字来自 `get_product_policy` 的结果。

## 常见错误（自查清单）

- 把客户的推断当成需求来做推荐 → 回头确认。
- 用话术卡里的一句话当产品能力依据 → 回到 `get_product_policy`。
- 推荐里出现"性价比最高""绝对不会错"这类主观判断 → 删掉，改成事实对比。
- 只给结论不给推理 → 补上"需求 → 事实"的对应关系。
- 建议下一步里出现替客户操作的动作 → 改成请客户自己确认或由销售跟进。

## 记录与反馈

- 推荐被采纳、修改或跳过时，用 `save_coaching_feedback` 记录，并注明被改动的部分（例如销售人员删掉了哪条理由），供话术和产品资料优化使用。
- 如果推荐过程中发现知识缺口（客户常问但没有对应政策或话术卡），在反馈中标注为知识缺口，交由审核队列处理。

## 边界与禁止

- 不修改产品事实、价格政策或话术卡；不发布知识。
- 不承诺效果、收益、审批结果，不代表公司做任何让步。
- 不代替销售与客户确认成交，不生成订单、合同或支付相关表述。
- 不处理异议攻防（交给 `objection-handling`）；不判断人工接管（走 `human-handoff`）。
- 需求不足时宁可只输出提问，也不要给一个听起来完整但没有依据的推荐。
