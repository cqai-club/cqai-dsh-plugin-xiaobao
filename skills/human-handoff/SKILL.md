# human-handoff

## 何时使用

- 通话中命中任一条人工接管条件时。
- `realtime-sales-coach` 输出 `human_handoff: true` 时。
- 销售人员点击面板上的「请求人工协助」时。
- 已审核知识不足以支撑回答，或转写质量太差无法判断客户在说什么时。

## 谁来判定

**转人工判定由代码执行**，不是靠模型自觉。规则命中后代码会直接提示，不等模型判断。本 Skill 的职责是：复核、补全交接材料、调用 `request_human_handoff`。

如果代码已经判定需要接管，不要因为"我觉得还能答"就取消。你可以补充风险说明，不能推翻判定。

## 接管条件（开发计划 §5.2 的 8 条）

1. 退款、赔付、投诉、法律或合同问题；
2. 未核实的功能、价格、优惠或效果承诺；
3. 医疗、金融、隐私、安全等高风险主张；
4. 客户要求内部底价、内部资料或其他客户信息；
5. 意图置信度或说话人识别低于阈值；
6. ASR 识别不完整，或客户与销售同时发言；
7. 已审核知识没有足够依据；
8. 客户明确拒绝，需要结束或转人工服务。

逐条核对，命中即建任务，并在交接材料中标明命中的是哪一条。多条同时命中时全部列出。

## 要做什么

1. **确认命中的条件**，写下编号和具体触发点（客户哪句话、哪一处置信度低）。
2. **收集客户原话**。用转写原文，不改写、不润色、不总结成"客户对价格不满意"。转写不完整就标注 `[转写不完整]`。
3. **整理已确认事实**。只放客户明确说过、或 `get_product_policy` / `get_customer_context` 明确返回的内容，每条带来源。
4. **列出未知信息**。影响后续处理、但当前不清楚的信息，写成问题。
5. **写风险原因**。为什么不能由 AI/销售自行处理；不写"风险较高"这类空话，要写触发机制（例如"客户提出退款并要求书面答复，涉及政策解释权限"）。
6. **附相关政策来源**。用 `get_product_policy` 取与本问题相关的政策条目 id、版本与生效期。取不到就写"无可用依据"，不要编。
7. **给建议处理方向**。一句话说明接手的同事该先做什么（核实哪项信息、由谁答复、走哪个流程）。不写具体承诺方案。
8. **调用 `request_human_handoff`** 建立任务，然后给销售人员一段**即时可用的话术**，用于稳住当前对话。

## 与客户沟通时的处理

接管任务建立后，销售仍需要把当前对话圆下去。给一句只做三件事的话：表示重视、说明需要核实或转由专人、给出明确的后续方式（不承诺时间点，除非政策中有）。

- 可以：`这个情况我需要请专门同事帮你确认，我先把你的问题完整记录下来。`
- 不可以：`我马上帮你申请退款` / `半小时内一定给你答复`。

## 输出契约（交接材料结构）

```text
接管条件：<§5.2 编号 + 触发点>
客户原话：<转写原文；不完整处标注 [转写不完整]>
已确认事实：
  - <事实>（来源：<policy id · 版本 · 生效期 / 会话确认>）
未知信息：
  - <具体问题>
风险原因：<为什么不能由 AI 或当前销售自行处理>
相关政策来源：
  - <policy id · 版本 · 生效期>  / 无可用依据
建议处理方向：<接手人第一步动作>
建议即时话术：<一句安抚 + 转接说明>
会话信息：<会话 id、时间、说话人标签质量说明>
```

字段约束：

- `客户原话` 必须是转写原文。交接材料是后续处理的依据，改写会造成事实偏差。
- `已确认事实` 与 `未知信息` 必须分开。推断不写入已确认事实。
- `相关政策来源` 只填本次工具真实返回的条目。空着可以，编造不行。
- `风险原因` 要能被接手人用来判断优先级。
- 不写入客户密码、证件号等与处理无关的敏感信息；需要时由接手人按权限查询。

## 交接后

- 用 `request_human_handoff` 记录任务；`save_coaching_feedback` 可记录销售对该交接提示的采纳情况。
- 交接后不再自动生成推进型建议；面板保留转写供接手人阅读。
- 交接不等于会话结束；客户继续说话时仍记录转写，但不再给促销类建议。

## 边界与禁止

- 不承诺退款、赔付、补偿、时限或任何处理结果。
- 不解释合同条款，不代表公司表态。
- 不向客户提供内部底价、内部资料或其他客户信息；客户索要时直接说明无法提供。
- 不因为"想先自己试一下"而延迟转人工。
- 不把交接材料写成产品推荐或二次销售机会。
- 不把未核实的推断写成已确认事实来让交接显得完整。
